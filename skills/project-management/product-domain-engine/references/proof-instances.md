# Proof Instances

Four products that already ran the Product Domain Engine, before it was named. Their existence is the empirical basis for the engine — the engine is not a hypothesis. It was identified by observing the recurring pattern across these four cases.

Each case below records: domain, formalization density, rhetorical-mode scores, what it proved, what it taught the engine.

## Instance 1 — `public-record-data-scrapper`

**Status:** GRADUATED  
**Organ traversal:** I → III → IV → V

### Domain
UCC public records across 50 U.S. states.

### Formalization density
- 60+ collection agents (one per jurisdiction)
- 2,055 tests
- Live deployment (Netlify)
- Paying subscribers
- Flagship README: 4,455 words

### Rhetorical-mode scores
| Mode | Score | Evidence |
|------|:-----:|----------|
| Logos | ■■■ | 60 agents, data schemas, normalization pipelines |
| Ethos | ■■■ | Flagship README, GRADUATED status, paying subscribers, deployment URL |
| Pathos | ■ | Functional B2B tool — minimal narrative; pathos was not the lever |
| Kairos | ■ | Steady B2B demand; no wave to ride; kairos is "always" |

**Dominant mode:** logos + ethos (density)

### What it proved
**Density creates gravity.** The 60 collection agents and 2,055 tests created an audience-attracting mass without any pathos investment. People found the project because it existed at sufficient density. The formalization *was* the marketing.

### What it taught the engine
1. Some domains do not need pathos. B2B utility lives on ethos density alone.
2. The flagship README is the highest-leverage ethos artifact — it converts logos mass into audience-visible credibility.
3. Test count is a credibility signal. "2,055 tests" tells the audience nothing technical; it tells them the system is serious.

### Engine-relevant pattern
**The Density Principle** — applicable to all domains: build enough real structure and traffic comes. Recorded in `references/cross-fertilization.md` (cross-domain pattern registry).

## Instance 2 — `styx-behavioral-economics-theory` → `styx-behavioral-art` → `peer-audited--behavioral-blockchain`

**Status:** Active, organ-traversing  
**Organ traversal:** I → II → III (full chain)

### Domain
Behavioral accountability via loss aversion and peer audit.

### Formalization density
- 9 theorem proofs
- Loss aversion coefficient: 1.955 (formal)
- 499+ tests
- 8 validation gates
- 4-platform implementation: NestJS + Next.js + React Native + Tauri

### Rhetorical-mode scores
| Mode | Score | Evidence |
|------|:-----:|----------|
| Logos | ■■■ | Dissertation-grade theory, theorem proofs, 4-platform deployment |
| Ethos | ■■ | Formal thesis, peer-audited design, deployment in progress |
| Pathos | ■ | Behavioral-art repo exists but emotional narrative is not customer-facing yet |
| Kairos | ■■ | Behavioral econ + DeFi both rising; peer accountability trending (BeReal, Strava) |

**Dominant mode:** logos (theory)

### What it proved
**Theory → Art → Commerce is a real pipeline.** Styx is the first product to traverse the full ORGANVM organ chain (I → II → III) end-to-end. Formal proofs derived art derived products. The traversal pattern is operational, not hypothetical.

### What it taught the engine
1. Some domains require deep theory before any product surface. Skipping Tier 2 would have produced a hollow shell.
2. The organ chain is real. Theory (I) → Art (II) → Commerce (III) is a generative sequence, not three independent products.
3. Theorem proofs are ethos artifacts. The audience does not read the proofs, but the *fact that proofs exist* lifts the trust ceiling.

### Engine-relevant patterns
**Theorem-Proving Methodology** — applicable to any domain that makes truth-claims (e.g. a chess creator brand's title-scoring formula could be validated theorem-style). Recorded in cross-fertilization registry.

**Multi-Organ Traversal Scoring** — the engine evaluates which organs each domain needs. Some domains (public-record-data-scrapper) skip organs; some (styx) traverse the full chain.

## Instance 3 — `wellness-practitioner-brand` (client engagement, anonymized)

> Client names, domains, and business details for this instance were removed from the public repository. What remains is the generic pattern the engagement demonstrated.

**Organ traversal:** I (light) → II → III

### Domain
A health/wellness practitioner whose knowledge spans several audience verticals, expressed as a hub-and-spoke brand: one hub site plus spoke sites for distinct audience entry points.

### Formalization density (typical shape)
- A navigable visual model of the practitioner's taxonomy (e.g. a node-based spiral or map)
- A small pillar system that groups the practitioner's protocols
- Hub-and-spoke topology across several domains
- Atomic brand components extracted into a reusable library
- Static-site stack (e.g. Astro + Tailwind + a static host)

### Rhetorical-mode scores
| Mode | Score | Evidence |
|------|:-----:|----------|
| Logos | ■■ | Architecture exists with a single configuration source of truth |
| Ethos | ■ | Pre-launch; credibility is gated on client feedback |
| Pathos | ■■ | Visual model is emotionally resonant; conversion tuning pending |
| Kairos | ■ | Practitioners are over-served on single websites; timing depends on the client's readiness, not the market |

**Dominant mode:** balanced (slight pathos lead)

### What it proved
**One practitioner's knowledge maps to multiple audience entry points through topology.** A hub-and-spoke architecture lets a single practitioner address multiple verticals without splintering the brand.

### What it taught the engine
1. Client-driven domains may need pathos before architecture. When a client needs to *see* the experience before the architecture is locked, run Tier 4 first and let Tier 3 follow.
2. Topology is a formalization output. A hub-and-spoke pattern is a logos artifact (it has rules) that functions as pathos externally (it makes the brand navigable and emotionally legible).
3. Physical-product derivation chains apply: a practitioner's protocols can become journals, cards, or cycle trackers derived from the formalization.

### Engine-relevant patterns
**Hub-and-Spoke Topology** — applicable to any domain with multiple audience entry points (e.g. separate community, course, and content domains for a creator brand).

**Brand Embedding Structure** — voice + naming + visual + narrative as a four-layer brand stack, recorded in the Phase 4 specification.

## Instance 4 — `chess-creator-brand` (client engagement, anonymized)

> Client names, metrics, and business details for this instance were removed from the public repository. What remains is the generic pattern the engagement demonstrated.

**Organ traversal:** I (light) → II → III → VI → VII

### Domain
Chess improvement at the amateur level, documented as entertainment. The hero's journey applied to the rating ladder.

### Formalization density (typical shape)
- A typed engine: title scorer, narrative framework, analytics, growth model
- A multi-section landing page
- A short list of identified market gaps
- A themed course catalog on a free-to-premium price ladder
- Trademark research and a documented business model

### Rhetorical-mode scores
| Mode | Score | Evidence |
|------|:-----:|----------|
| Logos | ■■ | Engine exists with types and tests; not yet deployed |
| Ethos | ■ | Small but growing audience; credibility still building |
| Pathos | ■■■ | Strongest pathos of any instance — underdog narrative, anime-style rank identity, emotional landing page |
| Kairos | ■■ | "Improvement journey" content niche rising; kairos open for community, gated for courses |

**Dominant mode:** pathos (narrative)

### What it proved
**The full Product Domain Engine can be run in one session.** Market-gap analysis → business model → landing page → course catalog → trademark research in about a day. The engine is fast when the domain is well known to the operator.

### What it taught the engine
1. Pathos-dominant domains lead with narrative. A named rank progression IS the formalization, not decoration.
2. Typed engine modules (title scoring, analytics, growth) are simultaneously logos (typed business logic) and the autopoietic observation instruments — they measure the deployed surface and feed back into formalization.
3. Single-session formalization is feasible for domains with strong pre-existing operator knowledge (an existing content archive plus the operator's own domain familiarity).

### Engine-relevant patterns
**Ki-Shō-Ten-Ketsu Narrative Framework** — four-act narrative structure (setup → development → twist → resolution) — applicable to how styx presents its thesis, how any domain structures a pitch deck.

**Named Rank System** — taxonomic / community-tier pattern (an ordered ladder of named ranks) — applicable to any domain with skill bands (Discord roles, course tiers, achievement systems).

**$0–$500 Price Ladder** — tiered pricing covering freemium → community → digital products → cohort → premium service. Mode-tagged in `composition-matrix.md`.

| chess-creator-brand | ■■ | ■ | ■■■ | ■■ | pathos | landing page + rank identity |

### Key observation

**Each instance leads with a different rhetorical mode.** The engine does not prescribe which mode dominates — the *domain's nature* determines it. B2B utility leads with logos. Theoretical product leads with logos. Client-brand leads balanced/pathos. Entertainment-community leads with pathos.

The engine's job is not to pick the lead mode. The engine's job is to ensure **all four modes are addressed** *regardless* of which one leads.

## Verification Of The Engine

Run `scripts/domain-audit.sh` against all four instances. The dominant-mode result should match the table above (with the documented caveat that the script reads structure, not voice — pathos detection is biased toward `brand/` directories and narrative files, so the chess-creator-brand instance will under-score on pathos in the script even though it is pathos-dominant in lived practice).

The audit is a *coverage* check. Quality assessment requires human reading.
